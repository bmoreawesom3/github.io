CS-470: Full Stack Development II

Taking a full-stack application to the cloud — re-architecting a container-based app into a serverless, cloud-native design on AWS, and weighing the trade-offs between containers and serverless along the way.

This course focused on migrating a full-stack application to a cloud-native architecture. The core work was moving from a Docker-based deployment to managed AWS services — using Lambda for serverless compute, API Gateway for the API layer, DynamoDB for NoSQL storage, and S3 for hosting — while reasoning about cost, scaling, and reliability at each step.

What I worked on

  • Designed a cloud architecture on AWS using S3, Lambda, API Gateway, and DynamoDB.
  • Containerized the application with Docker before migrating to managed services.
  • Built serverless functions and REST APIs to replace server-based backend logic.
  • Modeled data in DynamoDB (NoSQL) and connected it to the API layer.
  • Integrated the frontend and backend into a complete, cloud-hosted solution.
  • Compared containers vs. serverless on cost predictability, scaling, and error isolation.

Reflection

This course sharpened my ability to design cloud architectures and to judge when serverless is the right call versus containers. I came away more confident integrating APIs, working with NoSQL data, and treating scaling, cost, and failure isolation as first-class design concerns — skills that map directly to roles like Cloud Developer, DevOps Engineer, Full-Stack Developer, and Solutions Architect.

Cloud & serverless takeaways

  • Scaling & error handling: Lambda scales automatically and keeps failures isolated to individual functions, so a microservice error stays contained to one component.
  • Cost model: serverless is pay-per-execution, so cost tracks usage, while containers give more predictable costs for steady, consistent workloads.
  • Elasticity & pay-for-service: lets a business absorb variable or seasonal demand without over-provisioning, pilot new features cheaply, and align spend with real usage.
  • Trade-offs of going serverless: you gain independent deployability, technology-choice freedom, and fine-grained scaling — at the cost of added system complexity, cold-start latency, and harder distributed debugging.
